# AgentVisor 0.1: устройство системы

Локальная версия для Windows и Linux, включая Docker.
Инструкции по проверке — в [testing.md](testing.md).

## Состав

```text
Браузер: обзор / задачи / модели / история / настройки
  └─ FastAPI, HTTP API, опрос состояния каждые 2 секунды
       ├─ SQLite WAL: задачи, версии цели, события, настройки
       ├─ supervisor: один активный запуск, рабочий поток
       │    └─ OpenCode: свежая сессия на каждую итерацию
       │         └─ локальный шлюз с адресом сессии
       │              ├─ наблюдение генерации и вызовов инструментов
       │              └─ MCP exec / poll / stop → управляемые процессы
       └─ LM Studio (CLI/REST) или Ollama (HTTP API), запросы через шлюз
```

Python 3.10+ (проверен 3.12), FastAPI, SQLite, psutil, httpx и официальный LM Studio SDK.
HTML/CSS/JavaScript без отдельной сборки. Node и OpenCode включены в Docker;
для нативного запуска OpenCode устанавливается отдельно.
Файловая блокировка защищает каталог данных от второго экземпляра приложения.
Launcher узнаёт работающий экземпляр по каталогу данных, даже если исходники
изменились. Хеш используется для сообщения о необходимости обновления.
Адрес публикуется после готовности HTTP API; при занятом порте выбирается
свободный в диапазоне 8420–8440. Последний порт хранится в launcher.json.

## Цикл и состояния

Основной путь: `draft → preparing → running → verifying → succeeded`.
Другие состояния: `recovering`, `pausing`, `paused`, `stopping`, `stopped`,
`blocked`, `failed`, `completed_unverified`. Очереди параллельных задач пока нет.

1. Проверить число итераций и время задачи.
2. Подготовить сервис модели, выбрать модель, если не задана, и обеспечить её загрузку.
3. Прочитать последнюю версию цели и подготовить документы.
4. Запустить новую сессию OpenCode с JSON-выводом и заданным профилем.
5. Собрать события, выходные токены, время и ошибки, ограничивая буферы.
6. Проверить DONE, версию цели, чек-лист и настроенную команду проверки.
7. Продолжить, восстановить, заблокировать или завершить задачу.

Событие `error` в JSON считается отказом даже при коде выхода 0. Таймаут, пауза и остановка
завершают дерево дочерних процессов. Windows: Job Object и psutil;
Linux: группа процессов и psutil. При восстановлении сверяются PID и время
создания. После аварии прерванная активная задача с `autonomous_recovery=true`
продолжается с диагностикой. Ручные пауза/остановка сохраняются; при отключённом
автовосстановлении прерванный запуск остаётся на паузе.
Во время работы на Windows блокируется автоматический переход в сон.

Общие пределы времени и итераций действуют всегда. В автономном режиме локальные
пороги ошибок/отсутствия прогресса включают сессию ремонта с диагностикой;
при `autonomous_recovery=false` они приводят к `blocked`. Счётчики учитывают
также неудачные итерации и сохраняются в SQLite. Прогресс определяется новыми
отметками чек-листа; изменение его пояснений не считается прогрессом.
Это наблюдаемая оценка плана, а не семантическая проверка качества изменений.

Восстановление различает сбой runtime/генерации, инструмента, независимой проверки,
контекстного бюджета и самого агента. Только отказ runtime/генерации или памяти
модели запрашивает её перезагрузку; пауза растёт экспоненциально до 300 секунд.
Для остальных отказов используется `backoff_seconds`. Ошибка команды не лечится
выгрузкой исправной модели. Ошибка проверки передаёт именно её результат,
код выхода и хвост вывода, а не предшествующий успешный ответ агента.

`recovery_context` хранит пять последних попыток, слой сбоя, ограниченные входы,
вывод/ошибки инструментов и отпечатки повторений. Отдельная память команд хранит
до 16 неудачных сочетаний команды, оболочки и каталога для текущей версии цели.
После двух одинаковых отказов `exec` требует изменить команду либо передать
`repair_note` с объяснением сделанного исправления. Память переживает новые сессии
и продвижение по чек-листу; новая версия цели отделяет прежние ошибки.
Текст пояснения не проходит формальную проверку истинности.

## Команды под управлением supervisor

На каждой реальной итерации шлюз публикует MCP endpoint на loopback со случайным
адресом сессии. OpenCode обнаруживает `agentvisor_process_exec`,
`agentvisor_process_poll` и `agentvisor_process_stop`.
Перед подключением native-инструментов `command_policy.py` читает эффективную
конфигурацию и разрешения выбранного/default агента через `opencode debug config`
и `debug agent` в каталоге задачи, с общим сроком 20 секунд. Полная конфигурация
с секретами провайдеров не сохраняется. Собственный сгенерированный opencode.json
исключается из такого чтения, пользовательские конфигурации остаются в силе.

Однородные allow/ask и простые deny-шаблоны команд поддерживаются; неизвестные
форматы, списки разрешённых исключений и специфические ask-шаблоны закрывают
доступ к новому исполнителю. При этом сохраняется исходный транспорт OpenCode.
Когда перенос возможен, встроенный Bash запрещается через `permission.bash=deny`,
а MCP получает унаследованное разрешение. `auto_permissions` (`--auto`) продолжает
определять автоматическое подтверждение, не отменяя прежние запреты.

Для deny-шаблонов команда PowerShell перед запуском разбирается
`Parser.ParseInput`: исходный текст передаётся кодированными данными и не выполняется
проверкой. Сопоставляются весь текст и отдельные команды, включая quoted `&`-вызовы;
динамические имена, изменение алиасов, определения функций, другая оболочка и
динамические аргументы затронутой запретом команды отклоняются. Bash с такими
ограничениями отклоняется, потому что эквивалентного проверенного разбора пока нет.
При `external_directory=deny` native-транспорт целиком недоступен: внешний путь
может передаваться аргументом при рабочем каталоге внутри проекта, а собственного
надёжного анализа таких путей нет. Сохраняется исходный evaluator OpenCode.
`external_directory=ask` наследуется MCP-инструментом как запрос разрешения.
Это консервативная проверка существующей политики команд, а не песочница для
кода дочерних программ.

`CommandSessions` создаёт процесс отдельно от транспорта OpenCode. Оболочка по
умолчанию — PowerShell в Windows и Bash в Linux, возможен явный выбор. PowerShell
получает код через `-EncodedCommand`, без промежуточной Bash-подстановки переменных.
stdout/stderr пишутся в файлы, поэтому дочерний сервер не удерживает открытый
канал вывода MCP. `exec`/`poll` ждут не более 1000 мс, плюс время создания процесса
и его очистки. Ответ содержит `process_id`, `status`, `exit_code`, хвост вывода
и пути логов. `running` не означает успешное завершение; состояние уточняется `poll`.

Фоновый сервер запускается прямой командой с `background=true`; готовность проверяет
отдельная команда. Повторный запуск идентичной ещё работающей команды возвращает
её существующий `process_id`. Каждый процесс имеет срок, ограниченный также бюджетом
задачи. Монитор проверяет его независимо от запросов модели и вызовов `poll`.
В одной итерации допускаются 16 активных и 128 созданных процессов. При достижении
8 МиБ любым stdout/stderr-логом процесс получает `output_limit`; порог проверяется
периодически и не является точным дисковым лимитом без возможного превышения.
Логи остаются в `.agentvisor/tasks/<id>/commands/<process_id>/`.

Пауза, остановка, конец итерации и закрытие шлюза завершают все принадлежащие ему
процессы, включая фоновые. Windows Job Object защищает дерево и при аварии владельца;
на Linux используются группы процессов. `stop` принимает только собственный
`process_id`. Эти сессии не предназначены для постоянных сервисов между итерациями.

`ToolTrace` фиксирует вызов на границе ответа модели до того, как CLI сообщит
о результате. Поэтому зависание после `step_start` сохраняет имя и входные данные
фактического незавершённого инструмента. Его срок не продлевается посторонними
токенами. Общий таймер молчания учитывает активность потока модели; проверки API,
stderr и повторный `step_start` сами по себе не подтверждают работу.

## Контекст и проверка

Документы задачи находятся в `<workspace>/.agentvisor/tasks/<id>/`:
GOAL.md, PROGRESS.md, DONE.md и opencode.json. Корневые документы проекта
не перезаписываются.
Редактор цели повышает её версию; она применяется на границе итераций.
Старый DONE архивируется. Перед принятием результата версия повторно проверяется
под блокировкой, включая изменение цели во время независимой проверки.

Необязательные дополнения через `/api/tasks/{id}/context` имеют отдельную версию.
Шлюз добавляет их как постоянный контекст рядом с исходной целью, сохраняя порядок
последующих ответов и результатов инструментов. Они не становятся новым сообщением
в конце каждого запроса и не требуют повторного подтверждения модели. Обновлённая
версия передаётся уже в следующем запросе текущей сессии. Успешный HTTP-ответ
подтверждает доставку, но не выполнение указаний. Пока дополнения не доставлены,
завершение задачи не принимается.

- `completed_unverified`: актуальный DONE и завершённый чек-лист; проверки нет.
- `succeeded`: дополнительно прошла команда проверки, заданная пользователем.
  Надёжность вывода зависит от полноты этой команды.

Команда проверки — массив аргументов, запуск без оболочки.
OpenCode получает инструкцию делать один шаг и документировать результат.
AGENTS.md проекта сохраняет силу. Это управление через инструкции и наблюдаемые
результаты, без формальной гарантии произвольного поведения модели.
Автоматические разрешения OpenCode включаются явной настройкой пользователя.

## Модели

Панель показывает установленные и загруженные модели. `tuning.py` формирует
ограниченный набор профилей по приоритету, памяти, поддержке инструментов и
пределу контекста. Калибровка проверяет до четырёх вариантов загрузки/генерации;
после замера RAM/VRAM перечитываются без кэша. Для удалённого runtime ресурсы
управляющей машины не считаются ресурсами сервера модели. Выбор кэшируется
на 24 часа по запросу, конфигурации оборудования и установленным моделям.

LMStudioService отделяет daemon, HTTP API и модель. Для локального адреса с
включённым manage_runtime сначала проверяется API; если он недоступен, при
необходимости устанавливается официальный llmster, выполняются lms daemon up
и lms server start, затем ограниченное ожидание готовности API. Ошибка доступа
401/403 не вызывает перезапуск. Запущенное приложение LM Studio используется
повторно. Отмена задачи проверяется между этапами и во время команд.

Команды сервиса выполняются отдельно от Job Object/групп очистки агентских
процессов: daemon должен пережить завершение CLI. Для остановки сохраняются
PID и время создания своего llmster; после перезапуска панели эти данные
сверяются заново. Перед остановкой проверяется отсутствие чужих моделей.
При выходе из панели сервис остаётся работающим; контейнер завершает свои
процессы при остановке Docker.

Модель загружается с явным контекстом и собственным идентификатором agentvisor-*.
Идентификатор зависит также от размещения GPU, Flash Attention и типов K/V.
`load_config.py` запускает SDK в ограниченном по времени, отменяемом процессе,
затем читает и сверяет фактическую конфигурацию. Auto для локальных GGUF
пробует FA с F16/Q8; Q4 требует ручного выбора. Неподдерживаемые настройки
не объявляются применёнными. При смене профиля выгружаются только свои экземпляры. Чужие экземпляры
не выгружаются. Перед использованием CLI сверяется порт управляемого сервера.
Один runtime должен обслуживаться одним контроллером AgentVisor:
межэкземплярной координации нет.

Удалённый LM Studio должен быть уже запущен. REST-адаптер проверяет фактический
контекст загруженной модели и сохраняет идентификаторы созданных им экземпляров
с привязкой к адресу сервера для последующей выгрузки. Docker по умолчанию управляет llmster внутри
контейнера; отдельный том сохраняет его установку, движки и модели. Внешний
сервер на хосте также поддерживается, но его процессы не запускаются из контейнера.
Ollama загружает установленную модель и удерживает её через API;
Compose может запустить сам сервер Ollama.

Перезагрузка локального LM Studio или Ollama запрашивается только для слоя
runtime/генерации. При переполнении контекст увеличивается, при ошибке памяти
модели уменьшается, если не нарушает уже установленный минимум входного запроса.
Ошибки памяти команды или проверки не меняют профиль модели. Повторы сохраняют
общий бюджет задачи и, при отключённом автовосстановлении, локальные лимиты.
Для удалённого LM Studio принудительная выгрузка чужих экземпляров не выполняется.

Во время execute каждые 5 секунд проверяются API и точный instance/context.
Первая ошибка попадает в журнал; вторая подряд возвращает runtime_unavailable,
останавливает дерево процессов и передаёт управление существующему recovery loop.
Успешная проверка сбрасывает счётчик. При паузе, остановке и между итерациями
фонового принудительного поднятия модели нет. Свежесть проверки видна в обзоре.
Соединения SQLite закрываются после каждой транзакции, включая записи watchdog.

Оценка памяти lms --estimate-only и короткий benchmark доступны отдельно.
CLI не принимает параметры FA/KV; такая оценка помечена defaults_only и не
выдаётся за точную стоимость профиля с другим кэшем. Native REST /api/v1/chat
возвращает скорость генерации отдельно от времени всего запроса. OpenCode
использует /v1/chat/completions: SDK-параметр reasoningEffort превращается
в reasoning_effort, native off/on переводятся в none/high. Температура и top_p/top_k
передаются явно, если пользователь их задал. Проверка фактического HTTP-запроса
есть в tests/smoke_opencode.py. Глобального перебора, оценки качества и гарантии
скорости на длинном запросе нет. Python SDK 1.5 не передаёт API-токен: для
аутентифицированного runtime авто не меняет FA/KV, а CLI/REST продолжают работать.
Скачивание весов LM Studio запускается из панели через REST API; идентификатор
задания сохраняется в SQLite, панель опрашивает объём и скорость. Завершённое
состояние сохраняется и остаётся видимым после остановки сервиса. Вес модели
не выбирается для скачивания автоматически. Для Ollama используется ollama pull.

## Запуск и доступ

- Windows: Start.cmd, виртуальное окружение и браузер.
- Linux: sh start.sh, тот же код Python.
- Docker: приложение с OpenCode, дополнительные Compose-файлы для Ollama и NVIDIA.
  Проект монтируется в /workspaces/project.

Порт по умолчанию доступен только на loopback. Настройки позволяют выбрать
127.0.0.1 или 0.0.0.0; network.json в каталоге данных сохраняет режим и случайный
код доступа. Все API-запросы с нелокальных адресов требуют этот код в HttpOnly
SameSite-cookie либо Bearer-заголовке. X-Forwarded-For не меняет адрес клиента.
Локальный браузер может получить код через настройки; контейнер дополнительно
выводит его при запуске. Код общий, отдельных пользователей и ролей нет.

API изменений также использует токен сессии и проверку Origin; TrustedHost
ограничивает имена хостов, CSP — источники ресурсов страницы. Нативный сервер
разрешает локальные IP, контейнер принимает дополнительные адреса хоста через
AGENTVISOR_ALLOWED_HOSTS. HTTP не шифрует код и данные. Публикация в Интернет
требует отдельных TLS и контроля доступа. Секрет модельного API задаётся
переменной окружения.

Применение адреса требует перезапуска. Endpoint /api/restart проверяет отсутствие
активной задачи и операции с моделью под общей блокировкой, запрещает новые
операции, затем корректно завершает сервер. Код выхода 75 просит launcher
запустить новый процесс с сохранёнными настройками. Прямой запуск uvicorn
не поддерживает управляемый перезапуск. Docker фиксирует внутренний адрес
0.0.0.0; публикацией на хосте управляет AGENTVISOR_BIND_ADDRESS в Compose.

## Метрики и следующие этапы

Каждая итерация сохраняет в SQLite ограниченную память передачи задачи:
следующий пункт, последние заявленные завершения, пять последних результатов
команд с event_id/временем/cwd/exit code и четыре исхода попыток. Повторная
команда заменяет прежнее наблюдение, включая переход от успеха к ошибке.
Новая версия цели начинает отдельную память. Запрос получает не весь журнал,
а JSON до 10000 символов без дополнительной генерации сводки.
Агент может сохранять факты со ссылками на доказательства, отвергнутые гипотезы
и следующий ход в MEMORY.md каталога задачи (goal_version, до 2000 символов).
Эти заметки явно помечаются как непроверенные утверждения агента; старые
результаты команд не доказывают актуальную готовность серверов или файлов.

После итерации recovery также группирует распознаваемые причины отказов:
отсутствующая зависимость/команда, занятый адрес, отказ соединения или точная
диагностическая строка. Ключ учитывает следующий шаг, слой сбоя и доступный cwd;
изменение оболочки команды не сбрасывает счётчик. Третий повтор переводит новую
сессию в диагностику минимальным воспроизведением, пятый требует альтернативного
подхода. Событие strategy_change содержит причину и число попыток. Голый timeout
или exit code не объявляются общей причиной. Это ограниченная классификация
вывода между итерациями, без дополнительного вызова модели и без гарантии
правильности предложенного ею ремонта; действуют прежние бюджеты и ручная пауза.

Панель показывает заявленные пункты плана, итог проверки, итерации,
восстановления, ресурсы, события и длительность. Скорость сессии — выходные
токены / суммарное время процессов агента, включая инструменты. Отдельный режим
графика показывает генерацию последнего завершённого ответа: метрику runtime
либо `(completion_tokens - 1) / (last_fragment - first_fragment)`, когда доступны
точный usage и достаточный интервал. Сетевые фрагменты не считаются токенами.
Метрики читаются отдельно от журнала, который показывает последние 200 событий.
Переданный моделью reasoning сохраняется без попыток восстановить отсутствующий текст.
SQLite хранит всю историю
без автоматического ограничения размера. Демонстрационные данные подписаны.
